Embedding and Indexing: Practical Design Notes

An embedding model maps text to a fixed-length list of numbers. The model is trained so that text with related meaning is likely to have nearby vectors. For document retrieval, the same embedding model must be used when indexing chunks and when embedding a user question. Mixing models generally produces incompatible vector spaces, which means similarity scores no longer have a dependable interpretation.

Small sentence-transformer models are a useful starting point for a local project. They can run on a developer machine, download automatically on first use, and generate vectors without sending document text to a hosted embedding API. The all-MiniLM-L6-v2 model is widely used for prototypes because it offers a compact footprint and reasonable semantic retrieval for English. It is not universally best: specialist legal, medical, multilingual, or code collections may benefit from an embedding model trained for that domain.

Embedding work should be batched. A batch is a list of chunks passed to the model together rather than a separate call for every chunk. Batching reduces repeated setup work, improves hardware utilization, and makes the indexing process much faster for a sizeable corpus. The right batch size depends on available memory. A batch of 32 texts is a conservative default for a small local project; a larger corpus or a GPU may justify a larger value. The indexer should make this setting easy to adjust.

Before inserting vectors into a similarity index, many systems normalize them to unit length. With unit-normalized vectors, an inner-product search ranks results by cosine similarity. This provides a convenient and efficient implementation with a FAISS IndexFlatIP index. IndexFlatIP is exact: it compares a query with every stored vector. Exact search is simple and excellent for a few thousand chunks. At much larger scales, approximate FAISS indexes trade a small amount of recall for lower latency and memory cost.

Persistence is essential to a practical application. Indexing can take time, especially when the embedding model must be downloaded or documents are numerous. A persisted vector index lets the query application start quickly and prevents accidental re-indexing whenever a user asks a question. Alongside the binary FAISS index, the application should save a JSON or database record mapping each vector position to chunk text and metadata. Without that mapping, an index can return an identifier but cannot show the user the evidence that identifier represents.

An indexing command is a valuable separation of concerns. It reads source documents, extracts text, creates chunks, embeds all chunks in batches, and writes durable artifacts. A separate query command reads those artifacts and performs only question-time work. This boundary is also safer operationally: a document update becomes an explicit re-indexing action rather than an unpredictable side effect of a chat session.

Index freshness deserves attention. If files change after an index was built, the stored vectors reflect old content. A production system can compare document hashes, modification timestamps, or a manifest to identify stale material. A beginner project can communicate the simpler rule clearly: run the indexer whenever the files under data change. Recording the embedding model in metadata is equally important, because changing models requires a complete rebuild.
